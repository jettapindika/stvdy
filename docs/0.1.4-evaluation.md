# Stvdy v0.1.4 — Figma vs implementation gap report, evaluated

## What this document is

An independent, code-verified evaluation of the external audit report
("Stvdy v0.1.4 — Figma vs implementation gap report"). Every item the audit
raised is listed here with a verdict, the evidence that settles it, and the
corrected claim where the audit was wrong.

The audit was a **static audit**: its author read the release notes, `docs/DESIGN.md`,
`docs/SPEC.md`, the router, feature folders and locale files, viewed one Figma
screenshot, and explicitly did not run the app or pixel-diff the frames. This
document re-verifies each claim against the tree, adds frame evidence where the
audit only had a `LIKELY`/`UNVERIFIED` label, and reports the issues the audit
missed.

## Method and revision anchor

- **Audited revision:** commit `4692865` (`release: v0.1.4 with Figma-aligned
  responsive UI`). All file:line references are against this commit, read from a
  clean detached worktree (`git worktree add --detach <tmp> 4692865`) so the
  uncommitted working-tree edits cannot contaminate a finding.
- **Why that matters:** the live working tree is **dirty** — 27 modified/untracked
  files carrying an in-progress, uncommitted Musicfy-inspired redesign (branch
  `feat/musicfy-display`, which has **zero commits**; `main` and the branch both

- **Verdicts:** `CONFIRMED` = the audit's claim is accurate against `4692865`.

## §1 — Bug: the streak cannot work on the web build — CONFIRMED

The audit's analysis is correct in every step of the chain. Traced at `4692865`:

1. `app/src/features/today/TodayScreen.tsx:68-70` builds **one** window for the
   whole screen — `from = now − 24h`, `to = now + 8d` — and passes it to
   `useTodayData` at `:72`. The comment at `:58-67` justifies the window only as a
   superset of the local day and the next seven; it says nothing about history.
2. `app/src/features/today/useTodayData.ts:218` forwards `window.from`/`window.to`
   straight into `useActivity(window.from, window.to)`.
3. `app/src/api/queries/study.ts:146-169` — `useActivity` forks on
   `hasLocalCache()`:
   - **Native** (`hasLocalCache()` true, `app/src/api/queries/synced.ts:23-25`:
     `platform.runtime() !== 'web'`): reads **all** `flashcard_review`,
     `quiz_attempt` and `study_session` rows with **no window filter** — the
     streak works.
   - **Web**: `GET /activity?from=&to=` (`study.ts:166-168`), so the server
     returns only the last 24 hours.
4. `crates/server/src/study.rs:274-320` filters each array by
   `reviewed_at`/`answered_at`/`started_at` in `[from, to)`; `window()` at
   `:322-338` requires `from` and defaults `to = from + 1 day`. The server
   implements the window it is given — it is not at fault.
5. `app/src/features/today/day.ts` — `streakDays()` (`:289-302`) walks back from
   today (else yesterday) and stops at the first empty day; `recentDays()`
   (`:269-278`, `RECENT_DAY_COUNT = 5` at `:79`) marks the last five local days.
   Both are pure and correct; they can only be as complete as their `activity`
   input.

**Net effect on the web build:** `streakDays` is capped at **2** (today plus the
tail of yesterday), a long real streak renders as 1, and when today is not yet
active and yesterday's activity predates `now − 24h`, the card renders the
`EmptyState` ("No study days yet"). The 5-cell strip can never fill more than two
cells.

**Card rendering:** `TodayScreen.tsx:391-427` — when `buckets.streakDays > 0` it
renders the heading with the flame, the 5-cell strip and the encouragement line;
when it is `0` it renders an `EmptyState` **and removes the strip entirely**. The
Figma frame always shows the card with the strip.

**Not affected:** `minutesToday`, `today`, `overdue` and `thisWeek` — all of today
lies inside `[now − 24h, now)`, so those numbers are correct on web.

**Why tests miss it:** `app/src/features/today/day.test.ts:215-330` always feeds
complete activity arrays; every `TodayScreen.test.tsx` case installs
`installFakePlatform('macos', …)` (`:137, 182, 209, 247, 296, 341`, via
`app/src/test/harness.ts:297`), so `hasLocalCache()` is true and the web REST
branch is never exercised.

**Suggested fix (audit's, endorsed):**

1. Give `useActivity` its own window, separate from the timeline window:
   `from = today − 30 days` (at minimum 5 days for the strip), `to = now`.
2. Drop the 8-day look-ahead for activity — irrelevant to the streak.
3. Decide whether to always render the strip at 0 days. The code comment
   (`TodayScreen.tsx:417-421`) argues a "0-day streak" is discouraging; the frame
   draws the card with the strip regardless. This is a design decision, not a bug.
4. Add a regression test on the **web path** (no local cache) with activity on 4
   consecutive days, asserting a 4-day streak. The existing suite cannot catch
   this by construction.

## §3 — Missing or partial screens and states

### 3.1 No real PDF viewer — CONFIRMED

- No rendering dependency: `app/package.json` lists no `pdfjs-dist`, `react-pdf`,
  `pdf.js` or `mupdf`. `pdfium-render` appears only in `Cargo.toml`/`Cargo.lock`
  and is used server-side for **text extraction**, not rendering
  (`crates/server/src/sources/parse.rs:50-75`).
- The client never fetches a document. The server routes exist and are **unused**:
  `crates/server/src/sources/routes.rs:83` (`/sources/{id}/file`) and `:87`
  (`/sources/{id}/preview`).
- A citation opens **text, not a page**: `app/src/features/chat/ChatScreen.tsx:258-320`
  (`CitationPanel`) renders `chunk.data.content` in a `<p>` (`:313`). The `Chunk`
  type (`app/src/api/queries/chat.ts:30-37`) is `id/source_id/page/idx/content` —
  no `bbox`/highlight rects.
- Uploaded PDFs have no open affordance at all: `WorkspaceScreen.tsx:468`
  `openable = status === 'ready' && source.url !== null`; the "Open source" link
  (`:509-517`) is an external `<a target="_blank">` and uploaded sources have
  `url === null`.
- The spec requires the opposite: `docs/SPEC.md:38` (bundled PDF viewer worker),
  `:110` (`pdfjs-dist`), `:526` (viewer scrolled to the page with the passage
  highlighted), `:690` (viewer feature list). None of it exists.

### 3.2 Frameless window / top bar at y=0 — CONFIRMED

- `src-tauri/tauri.conf.json` window block sets `title/width/height/minWidth/minHeight/resizable`
  and **no `decorations: false`** — the window is decorated.
- `app/src/styles.css` — `.drag-region { height: 0 }`; `.window-frameless .drag-region
  { height: 2.25rem }`. `.window-frameless` is applied **nowhere** in TSX.
- Deliberate and documented: `Shell.tsx:46-53`, `TopBar.tsx:34-42`,
  `docs/DESIGN.md:340-343`.

### 3.3 Auth Help / Privacy / recovery links — CONFIRMED

- `AuthLayout.tsx:23-25`: "The frame's 'Need help?' and 'Privacy' links are
  deliberately not rendered: neither has a route in this app."
- No forgot-password anywhere: `SignInScreen.tsx` has no such link; the router
  registers only `/signin`, `/signup`, `/verify`, `/verify-email`, `/auth/callback`;
  a repo-wide search for `forgot|password_reset|reset_password` returns nothing in
  client or server.

### 3.4 Printed cheatsheet not aligned — CONFIRMED

- `templates/cheatsheet.v1.html` uses its own palette: `--accent:#2563eb`,
  `--accent-dark:#1e3a8a`, `--ink:#1f2937`, `--rule:#d1d5db`, plus hardcoded
  Tailwind blues/violet. No value matches an app token (app action colour is
  indigo `#4f46e5`).
- Documented deferral: `docs/DESIGN.md:372-379` — the cheatsheet is a print
  artifact with its own constraints (ink coverage, A4 breaks, KaTeX metrics) and
  reconciling it is Phase 6 work with a real print test.

### 3.5 Command palette has no server-side search — CONFIRMED

- `CommandPalette.tsx:35-37` states it verbatim: it does not search message text
  or chunk contents and does not call a search endpoint.
- The index is built only from existing screen queries (`useWorkspaces`/`useTasks`,
  and `useQueries` over source/flashcard keys), all gated `enabled: open`.
- A search of `app/src` for `/search` returns nothing; `docs/DESIGN.md:344-345`
  records the limitation.

### 3.6 Onboarding Language / Timezone / Reminders — CONFIRMED

- `SignUpScreen.tsx:26-27` `FIELDS = ['email','password','device']` — no language,
  timezone or reminder input.
- No onboarding flow exists (search for `onboard|first run|firstRun|setup wizard`
  across `app/src` and `crates/server/src`: no matches).
- Those settings are reachable only **post-signup** in Settings:
  `SettingsScreen.tsx:84` `SECTIONS = ['account','study','calendar','devices','appearance']`,
  with timezone, reminder channels and language inside those sections.

### 3.7 Scanned-PDF error state — PARTIALLY CONFIRMED

- **Detected server-side (correct):** `crates/server/src/jobs/handlers/ingest.rs`
  returns a permanent failure `"no extractable text: the document may be a scan"`
  when every page is blank, and `"chunking produced no chunks"` when chunking
  yields nothing; text sources get `"the document has no text"`
  (`crates/server/src/sources/parse.rs`).
- **Not localized:** no scanned/OCR key exists in `en.json` or `id.json`.
- **Raw server sentence shown verbatim:** `WorkspaceScreen.tsx:481-483` renders
  the server's `errorText`, so an Indonesian student sees an English server string.
- The spec named the intended copy: `docs/SPEC.md:517` ("This PDF looks scanned.
  Text recognition isn't available yet.").
- Verdict: the failure is detected and surfaced (not silent), but it is not the
  spec's message and not localized — hence **PARTIALLY**, and it is the cheapest
  of the twelve to close.

### 3.8 Missing-citations state — CONFIRMED

- The server always emits the `citations` event, even when empty
  (`crates/server/src/chat/sse.rs:24-31`), so a zero-citation answer arrives as an
  empty array.
- The client renders **nothing**: `MessageList.tsx:214-230` `SourceCount` returns
  `null` when the distinct source count is 0. There is no "this answer is
  uncited" notice.
- The string that would fit, `honesty.notInSources`, is used only by
  `ReportScreen.tsx`, never by chat.
- Spec: `docs/SPEC.md:526` ("Based on N sources") and `:689` (a "not-in-sources"
  chat variant).

### 3.9 Signed-out landing absent — CONFIRMED

- `AuthLayout.tsx` renders only a wordmark, one card, and a footer
  (`auth.metadata` = "STVDY / ACCOUNT"). No signed-out message, reason or action.
- `App.tsx` sends a signed-out session straight to `/signin` with no explanation.
- "Signed out" copy exists only as an API-error notice (`en.json` `error.unauthorized`
  / `error.token_expired`), shown when a request 401s — not on deliberate sign-out.
- There is no sign-out control outside the Devices screen; the account group in
  the top bar is a `Link to="/settings/account"`.

### 3.10 Admin sidebar (6 items) — CONFIRMED gap

- The Figma frame (`var/frames/figma/admin-dashboard.png`) shows a left rail with
  six items: **Overview / User activity / Payment audit / Provider costs /
  Access & roles / Admin settings**.
- `app/src/features/admin/AdminScreen.tsx` is a **single scrolling page** of
  `<Section>` blocks — users, margin summary, payments, margin report, tripwire.
  There is no `nav`/`aside`/sidebar and no item list.
- The audit's claim (Figma has a sidebar; code does not) is therefore **correct**.
  An earlier internal pass mis-read this as "refuted" by checking only whether the
  code had a sidebar, without comparing to the frame. The frame settles it: this is
  a missing surface, not a refuted claim.

### 3.11 Tasks board drag-and-drop — CONFIRMED

- `TaskBoard.tsx` renders a static 3-column grid (`grid-cols-1 … md:grid-cols-3`)
  with `COLUMN_ORDER = ['todo','doing','done']`; each card is a static `<article>`
  with buttons.
- No DnD anywhere: search for `onDrag|draggable|dragStart|dragOver|DndContext|sortable`
  returns nothing; `app/package.json` has no `dnd-kit`, `react-dnd` or
  `react-beautiful-dnd`.
- Whether the frame *implies* DnD is a design question the audit correctly left open;
  the code fact is that there is none.

### 3.12 Client-side math rendering — CONFIRMED

- `app/package.json` has no `katex`, `mathjax` or `react-katex`; a search of
  `app/src` for math rendering returns nothing.
- KaTeX is **print-only**: `templates/cheatsheet.v1.html` loads KaTeX, vendored
  under `assets/katex/` and served by the server. It never reaches the app bundle.
- Chat's renderer handles only a tiny markdown subset (inline code / bold / italic /
  citation markers), so a formula in an answer or a flashcard renders as literal
  `$…$`.

## §4 — Release-level gaps — CONFIRMED (two corrections)

Every gap is real. Two points in the audit's framing need correcting, and one
sub-gap the audit lists separately is best read together with the others: all six
sit at the **credential / execution boundary**, not in the code. The config, the
workflows, the verification scripts and the tests all exist and are internally
consistent; what is missing is the certificates, keys and hosts.

### 4.1 No iOS build — CONFIRMED

- The iOS **bundle config and the generated Xcode project are committed**:
  `src-tauri/tauri.conf.json` `bundle.iOS` and `src-tauri/gen/apple/`
  (`project.yml`, `Info.ios.plist`, `Podfile`, `ExportOptions.plist`,
  `stvdy-shell.xcodeproj/`, `ShareExtension/`).
- **Correction to the audit's implication:** it is not that nothing iOS exists; it
  is that (a) `bundle.iOS` has **no `developmentTeam`**, so `tauri ios build`
  cannot complete, and (b) **no CI job builds iOS** — `ci.yml` and `release.yml`
  have no iOS job, and `justfile` has no iOS recipe. `ci.yml`/`release.yml` only
  run `TAURI_ENV_PLATFORM=ios npm run build`, which builds the SPA assets alone.
- Documented status: `docs/RELEASE.md` records the iOS build (M1) as PASS-with-caveat
  (the CLI's runtime precondition was bypassed) and the TestFlight upload (M11) as
  **NOT DONE**. `var/release-v0.1.4-notes.md` lists only macOS DMG, Windows EXE and
  Android APK.

### 4.2 No updater manifest — CONFIRMED

- `tauri.conf.json` sets `createUpdaterArtifacts: true` and a `plugins.updater`
  block, but **no `latest.json` exists anywhere** in the tree, and the `pubkey` is
  the literal placeholder `<the operator's minisign public key>`.
- `release.yml` builds and signs `latest.json` but states it has never run;
  `unsigned-artifacts.yml` (the path v0.1.4 used) states it produces none.
- Consequence, stated in-tree: `docs/RELEASE.md` calls it a "safe-but-useless
  updater" — every signature fails to verify. Installed apps get no update prompts.

### 4.3 macOS signing — CONFIRMED (one stale comment)

- No `signingIdentity` is committed (deliberate; asserted by a test in
  `crates/server/tests/release.rs`). The identity arrives only from CI secrets;
  v0.1.4 shipped **unsigned and unnotarized**.
- **Correction:** `scripts/notarize-macos.sh` **does exist** (295 lines), so the
  comment in `release.yml` claiming it "is not in the tree yet" is **stale**. The
  guard step that checks for it would pass.
- The blocking prerequisite is a credential (an Apple Developer ID certificate),
  not code.

### 4.4 Windows signing — CONFIRMED

- No `certificateThumbprint` is committed; **no `signtool` invocation exists**
  anywhere. Signing is delegated to the Tauri bundler reading `WINDOWS_CERTIFICATE`.
- The release workflow **warns rather than fails** when the certificate is absent,
  so an unsigned installer ships as a "known degraded state".
- v0.1.4's Windows EXE is unsigned; SmartScreen warnings are expected.

### 4.5 Staging API endpoint; server not shipped — CONFIRMED

- `app/src/api/client.ts` bakes `VITE_API_BASE_URL` into the bundle at build time,
  with a `http://localhost:8080` fallback. `.env.example` ships only that dev
  fallback; no deployed origin is committed.
- The release workflow requires the origin as a build input (default
  `https://stvdy.ztvn.my.id/api`), refuses `localhost`, and asserts the origin is
  in the CSP `connect-src` — but **nothing committed pins an artifact to a server**,
  and the server is not in the installer assets.
- The only host in use is a trial host (per `docs/ASSUMPTIONS.md` A45), not a
  production host.

### 4.6 Musicfy redesign not in v0.1.4 — CONFIRMED

- Zero `musicfy` references in `app/src`. The branch `feat/musicfy-display` and
  `main` both point at `4692865`; the branch has **zero commits**.
- `var/release-v0.1.4-notes.md` states it explicitly.
- **Caveat for a reader:** the working tree is dirty with the uncommitted redesign
  (27 files), and `docs/DESIGN.md` in that dirty tree describes the redesign as
  current and "verified". Read `docs/DESIGN.md` **at `4692865`**, not in the live
  tree, when checking any v0.1.4 design claim.

## §5 — Deliberate deviations — CONFIRMED (all three)

### 5.1 `--border-strong` instead of Figma's `#DDE0F0` — CONFIRMED

- At `4692865`, `--border-strong` is `#7E85A6` light / `#6A789D` dark
  (`app/src/styles.css`, mirrored in `app/src/tokens/tokens.ts` and
  `docs/DESIGN.md:67`).
- The deviation is reasoned in-tree: Figma's `#DDE0F0` measures ~1.25:1 on the
  page ground while the same sheet states a 3:1 control-boundary target, so
  `.field` and `.btn-secondary` take `--border-strong` (~3.44:1). Every other
  surface takes the design's `--border`. Enforced by `tokens.ts`'s `PAIRS` at the
  3:1 UI floor and by `contrast.test.ts`.
- **Correction:** an internal pass reported `docs/ASSUMPTIONS.md` A102 as "stale"
  because it quotes `#7E85A6`/`#6A789D`. At `4692865` those values are **exactly**
  what ships, and `DESIGN.md` repeats them — **A102 is accurate for v0.1.4**. The
  mismatch came from reading the dirty Musicfy tree (`#7E7E8E`/`#838390`), which
  is not this release.

### 5.2 Dark mode derived from tokens — CONFIRMED

- At `4692865`, dark mode is a real themed block:
  `app/src/styles.css` `@media (prefers-color-scheme: dark)` carries the full dark
  token set, mirrored in `tokens.ts`. There is **no `.dark` class and no `dark:`
  utility** in `app/src`, per the documented rule (`docs/DESIGN.md:331`).
- Only 1 of the 54 frames is dark (plus a "Study workspace / Dark" frame); every
  surface is expressed in tokens so a new screen works in dark on its own.
- **Correction:** an internal pass attributed the v0.1.4 dark-mode mechanism to
  `app/src/lib/appearance.ts` + `ThemeSync.tsx`. Those files **do not exist at
  `4692865`** — they are Musicfy-era additions. At v0.1.4 dark mode is the OS media
  query plus the Settings theme select. Likewise, an internal pass reported
  `docs/ASSUMPTIONS.md` A358's dark values (`#1B2435`, `#B4BDCF`) as "stale"; at
  `4692865` those are exactly what ships and what `DESIGN.md` records — **A358 is
  accurate for v0.1.4**.

### 5.3 Timezone instead of the "AUTUMN 2026" term label — CONFIRMED

- `Sidebar.tsx:148-155` states the term label has no data source and is not
  invented; `:156-171` renders the account timezone. `docs/DESIGN.md:233` records
  the same. There is no term/semester datum anywhere in the app.

## §6 — "Appears implemented" — CONFIRMED, with one nuance

Every route or component the audit lists exists at `4692865`, with these
corrections:

- **`flashcards` is not a route.** It ships as a Studio **panel** inside the
  workspace (`app/src/features/studio/FlashcardsPanel.tsx`, rendered under
  `StudioSection` in `WorkspaceScreen.tsx`). The nearest routes are
  `/workspaces/:workspaceId` and the deck review `/study/:deckId`. There is no
  `/flashcards` path.
- **`calendar` and `tasks` are redirects into the planner** (`/planner?view=calendar`,
  `/planner?view=tasks`), not standalone destinations — by design
  (`docs/DESIGN.md`), because notifications and bookmarks already name them.
- **`pricing` exists only when the build-time `__PURCHASE_UI__` constant is true**
  (`app/vite.config.ts`), i.e. it vanishes from store builds. This is the intended
  billing-policy split, not a gap.

Confirmed present: Today (including offline), Workspaces (list), Workspace

## §8 — Issues the audit did not find

Five further issues, verified at `4692865`. Two are user-visible defects.

### N1 — No error boundary; a render error shows react-router's developer page (high)

- `app/src/router.tsx` sets **no `errorElement`** on any route, and `main.tsx`
  mounts `RouterProvider` with nothing wrapped around it. There is no
  `ErrorBoundary`/`componentDidCatch`/`getDerivedStateFromError` anywhere in
  `app/src`.
- A render error therefore shows react-router's default page: `<h2>Unexpected
  Application Error!</h2>` with the **JS stack trace** and developer copy —
  unstyled, English-only, no route back.
- Nothing catches errors in event handlers or async callbacks; the `#root is
  missing` throw in `main.tsx` is outside the router entirely.
- No test covers it (`router.test.tsx` asserts only route reachability).

### N2 — `useTodayData().failed` is dead, so a failed read renders as "nothing due" (high, web build)

- `useTodayData.ts` computes `failed: queries.some(q => q.isError)`; **nothing
  reads it** (`TodayScreen.tsx` never references it).
- On the web build, `app/src/platform/web.ts` hardcodes `sync.status()` to
  `{ state: 'synced', … }` and `onStatus` never fires, so the offline band cannot
  appear. With the API unreachable, all reads error, `dueCards` falls back to 0,
  `setup.counts` to `{0,0,0}`, and Today renders the **"set up your account"
  checklist with 0/0/0** plus empty-state "nothing due" blocks.
- That is a network failure presented as "you have nothing to study", contradicting
  the screen's own contract and the `EmptyState` rule that a state must name its
  cause. Every other screen gets this right; Today is the outlier, and the field
  that would fix it already exists.
- Test gap: the offline suite exercises only the native path.

### N3 — `document.title` is never set per route (WCAG 2.4.2, Level A) (medium)

- `app/index.html` hardcodes `<title>Stvdy</title>`; nothing in `app/src` ever
  writes `document.title`. Every screen announces the same title to a screen reader
  and every browser tab. The app already solves the sibling problem for `<html lang>`;
  the title was simply left static, and axe does not check it in jsdom.

### N4 — CSP still allow-lists the dev API origin; asset scope is broad (medium)

- The packaged CSP `connect-src` still carries `http://localhost:8080` (the dev
  fallback baked by `client.ts`), and omits `base-uri`/`form-action`/`frame-src`.
  So a packaged desktop app will fetch anything a process on the user's :8080 serves.
- `assetProtocol` scope allows the whole app-data tree with a single deny on one
  subdirectory — broader than needed for the shell's own data.

### N5 — The automated a11y gate covers ~10 of ~30 screens (medium)

- `axe-core` is imported in one file and `expectNoA11yViolations` in three tests:
  the shared `a11y.test.tsx` (11 cases), `QuizScreen.test.tsx` and the styleguide
  gallery. No axe run exists for Settings, Admin, the auth screens, Dashboard,
  Tasks/board, the Studio panels, Pricing/Checkout/Billing and several others —
  including the largest screen in the app (Settings).

**Areas checked and found clean:** accessibility attributes/focus/skip link,
i18n completeness (enforced by a source-scanning test), responsive breakpoints,
loading states on every data-fetching screen, `.env.example` hygiene, mobile
navigation, SSE transport and its error handling, and asset handling (no
`<img>`/CDN loads; fonts self-hosted). Not re-listed here.
