# Phase 5. Quiz. Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use `superpowers:subagent-driven-development`
> or `superpowers:executing-plans` to implement this plan task-by-task. Steps use
> checkbox (`- [ ]`) syntax for tracking.
>
> Contracts are fixed in `docs/superpowers/plans/2026-10-11-study-os-master-roadmap.md`.
> This plan implements them; it never redefines them. Where this plan and the
> roadmap disagree, the roadmap wins and this file is the bug.

**Goal:** a student selects sources and gets a quiz generated from them, with every
question linked back to the chunk it came from and an explanation of why the answer is
right. They answer it, each answer is recorded as an append-only attempt, and the quiz
reports a score plus a weak-topic summary grouped by source and page.

**Architecture:** the score is **derived**, never authored — it is computed from the
attempts at read time, exactly as Phase 4 derives a card's schedule from its reviews.
That is what makes attempts from several devices conflict-free: an attempt is an
append-only fact with a client-generated id, so a replayed or duplicated write applies
once and no two devices can disagree about a stored score. Generation is one
`generate_quiz` job: strict-JSON prompt composition through the Phase 4 composer, one
retry on a parse failure, and a refund if the job fails for good. Grading is
deterministic for MCQ (the server owns it) and self-assessed for short answer (the
student marks it after seeing the model answer), because no string comparison can judge
free prose and a second model call per answer would cost more than the quiz did.

**Tech Stack:** Rust (core + server, no new crates), Postgres/sqlx, React + Vite +
TypeScript + Tailwind, TanStack Query.

**Exit gate (observable, from the roadmap):** generated quiz; attempts scored;
weak-topic summary grouped by source/page.

**Two roadmap gates are not optional here:**
- Gate 5, accessibility: the quiz screen states the check performed and the result.
- Gate 6, Indonesian end to end: an Indonesian source generates Indonesian questions,
  each question's `label` resolves to a real chunk of that Indonesian source, and the
  weak-topic summary names that source. Both the `{{output_language}}` default and the
  label map fail *silently* for Indonesian while English tests stay green, which is why
  this is a gate.

## Global Constraints (copied from the roadmap; every task includes these)

- **No `unwrap()` in non-test code.** Typed errors mapped to HTTP status codes.
  Prompts live in versioned modules, never inline. `tracing` structured logs with
  request ids; log latency for retrieval, LLM calls, sync pull/push, jobs, webhooks.
- **Server is the only source of truth.** Clients never call LLM directly. All heavy
  work is server-side. Generation is async with visible progress.
- **Offline writes are limited to:** tasks, events, flashcard reviews, quiz attempts,
  study sessions, settings. Everything else queues nothing. `quiz_attempts` is on that
  list, which is why an attempt carries a client-generated id.
- **All times:** stored `timestamptz` UTC + user IANA timezone (default
  `Asia/Jakarta`). Local-date math only through `chrono-tz`.
- **Credits (from `config/plans.toml`, never a literal):** `quiz_10 = 6` per ten
  questions. Plan limits: free `quizzes_per_month = 2`, pro and power `unlimited`.
- **Entitlements:** no limit is hardcoded; every limit is read from `config/plans.toml`
  through `crates/server/src/limits.rs`. Errors serialize to
  `{ code, message, min_plan?, limit?, used? }`.
- **Quality gate:** `cargo fmt --check`, `cargo clippy --all-targets -- -D warnings`,
  `cargo test`, `npm --prefix app test`, `npm --prefix app run build`, the `src-tauri`
  trio, `cargo sqlx prepare --workspace --check`.
- **UI language English**, but Indonesian documents and queries must work end to end
  (`simple` tsvector config + multilingual embeddings).

## Decisions this plan pins (so parallel work cannot diverge)

1. **The score is derived, never stored.** `GET /quizzes/:id/results` computes it from
   the attempts on every read. There is no `score` column, so there is no second place
   for the truth to live and no way for two devices to disagree about it.
2. **An attempt is append-only with a client-generated id.** `POST /quizzes/:id/attempts`
   accepts an optional `id`; absent, the server mints one. The insert is
   `on conflict (id) do nothing`, and the response carries `applied: bool`, so a client
   that retries after a lost response can tell whether its write landed instead of
   silently double-counting. Same rule and same reason as `flashcard_reviews`.
3. **MCQ is graded by the server; short answer is self-assessed.**
   - MCQ: the server compares the submitted option text to `quiz_questions.answer`
     after normalisation (trim, case-fold, collapse internal whitespace). The client's
     `correct`, if sent, is **ignored** — grading is the server's.
   - Short answer: the student reveals the model answer and `key_points`, then marks it.
     The client sends `correct`. No string comparison can judge free prose, and a second
     model call per answer would cost more than generating the quiz did.
   - `quiz_attempts.correct` stays nullable: an attempt with no grade yet is honest,
     and it is excluded from the score's denominator rather than counted as wrong.
   - This matches the app's existing pattern — a Phase 4 review is also a self-reported
     grade — so a student learns one mental model, not two.
4. **The answer a client submits is the option *text*, never a letter or an index.**
   The prompt already tells the model to copy the correct option verbatim into `answer`,
   so text is the one representation both sides already agree on. The SPA's radio value
   is the option string.
5. **`quizzes_per_month` counts quizzes, not questions.** Free is 2. Counting questions
   would make a single ten-question quiz exceed it, which is plainly not what the name
   or the matrix means. The reservation is still explicit: the count includes this
   month's `quizzes` rows **plus** the quizzes still `generating`, and the request
   reserves 1.
6. **The monthly cap is enforced exactly as Phase 4's now is** — one transaction
   holding the per-user advisory lock, the count, `enforce_batch`, `credits::spend_in`,
   the reserving quiz row, then commit. Counting outside that transaction is the bug
   Phase 4 shipped and then fixed: a quiz that is still generating has no rows in
   `quiz_questions`, so a count that ignores it reads zero and the cap can be exceeded
   by asking twice in a row.
7. **`quiz_questions.chunk_id` is the source link, and a label that was never sent costs
   the link, not the question** (A17). The count of dropped labels is recorded, because
   a rate that climbs means the prompt or the model changed.
8. **The weak-topic summary groups by the question's chunk's `(source_id, page)`,**
   weakest first, and reports unlinked questions in their own bucket rather than
   dropping them. A summary that silently omits the questions it could not attribute
   would look better and mean less.
9. **`GET /workspaces/:id/quizzes` is an addition beyond the spec's route list**, for
   the same reason Phase 4 added `GET /workspaces/:id/decks`: the Studio panel has to
   list what exists and poll the ones still generating, and the client must not be the
   only place that knows how to enumerate them.
10. **The refund path is a deliberate mirror, not an abstraction.** `decks` and
    `quizzes` each need a "claim the row, zero `credits_spent`, refund once" sequence,
    and the claim is a table-specific `update … where status = 'generating' returning id`
    that cannot be parameterised by table name without interpolating SQL. Two call sites
    is not yet an abstraction; Phase 6's report job will make three, and the extraction
    happens there with the third in hand.
11. **`generation::quiz` and `quiz` are different things** and are named for it:
    `crates/core/src/generation/quiz.rs` turns the model's reply into typed questions;
    `crates/core/src/quiz.rs` is about answering them (grading and the summary).
12. **The requested `types` is stored, and is not the same fact as a question's
    `kind`.** The generation job runs after the request returns, so it has to rebuild
    the same prompt, and `{{types}}` is one of that prompt's settings: without a column
    the job could not know whether the student asked for mcq, short or mixed, and would
    have to guess. This is the same reason `requested_count` is stored. Each generated
    question's own `kind` is a different fact, is what the client renders, and is
    already on `quiz_questions`.

```rust
pub const QUIZ_V1: &str = include_str!("../../../../prompts/quiz.v1.md");

pub enum ModuleId {
    FlashcardsV1,
    QuizV1,
}

impl ModuleId {
    /// Every module, for the contract sweep in `tests/prompts.rs`.
    pub const ALL: [ModuleId; 2] = [ModuleId::FlashcardsV1, ModuleId::QuizV1];

    pub fn version(self) -> &'static str {
        match self {
            ModuleId::FlashcardsV1 => "flashcards.v1",
            ModuleId::QuizV1 => "quiz.v1",
        }
    }

    pub fn text(self) -> &'static str {
        match self {
            ModuleId::FlashcardsV1 => FLASHCARDS_V1,
            ModuleId::QuizV1 => QUIZ_V1,
        }
    }

    /// The variables the module's own text (and the JSON contract) uses.
    ///
    /// `difficulty` and `types` are `Caller` rather than `Optional` on purpose: a
    /// default would make "mixed, medium" the silent meaning of an absent setting,
    /// and the student's request would then differ from what they got.
    pub fn variables(self) -> &'static [(&'static str, VarKind)] {

            ModuleId::FlashcardsV1 => &[

                ("output_language", VarKind::Optional(SOURCE_LANGUAGE)),

            ModuleId::QuizV1 => &[
                ("count", VarKind::Caller),
                ("difficulty", VarKind::Caller),
                ("types", VarKind::Caller),
                ("output_language", VarKind::Optional(SOURCE_LANGUAGE)),
            ],
        }
    }

    pub fn base_sections(self) -> &'static [&'static str] {
        match self {
            ModuleId::FlashcardsV1 | ModuleId::QuizV1 => TASK_BASE_SECTIONS,
        }
    }
}
```

```rust
//! The quiz JSON contract (`prompts/quiz.v1.md`), parsed and resolved.

use uuid::Uuid;

use crate::citations::ContextLabels;
use crate::generation::GenerationError;

/// The most questions one reply may carry. Above the largest request the API
/// accepts, so a model that ignores `{{count}}` cannot store an unbounded quiz.
pub const MAX_QUESTIONS_PER_REPLY: usize = 60;

/// How many options an MCQ must have. The prompt says four; this is what makes it
/// enforceable rather than aspirational.
pub const MCQ_OPTIONS: usize = 4;

#[derive(Debug, Clone, serde::Deserialize)]
#[serde(deny_unknown_fields)]
pub struct QuestionsFile {
    pub questions: Vec<GeneratedQuestion>,
}

/// The reply, exactly as `prompts/quiz.v1.md` documents it.
///
/// `options` and `key_points` are `Option` because the module writes an explicit
/// `null` for the field the kind does not use, and `deny_unknown_fields` means a model
/// that invents a field produces a parse error and a retry rather than a question
/// with a silently dropped field.
#[derive(Debug, Clone, serde::Deserialize)]
#[serde(deny_unknown_fields)]
pub struct GeneratedQuestion {
    pub kind: String,
    pub prompt: String,
    pub options: Option<Vec<String>>,
    pub answer: String,
    pub explanation: String,
    /// The chunk label the question came from, as shown inside `<sources>`.
    pub label: u32,
    pub key_points: Option<Vec<String>>,
}

/// One question with its chunk resolved, or `chunk_id: None` when the label was not
/// in the context (A17: dropped, never guessed).
#[derive(Debug, Clone)]
pub struct ResolvedQuestion {
    pub kind: String,
    pub prompt: String,
    pub options: Option<Vec<String>>,
    pub answer: String,
    pub explanation: String,
    pub key_points: Option<Vec<String>>,
    pub chunk_id: Option<Uuid>,
    pub label: u32,
}

#[derive(Debug, Clone, Default)]
pub struct QuizParseOutcome {
    pub questions: Vec<ResolvedQuestion>,
    /// Labels the model cited that were not in the context, deduplicated and sorted.
    pub dropped_labels: Vec<u32>,
}
```

`parse_questions` strips a code fence (same helper as `flashcards.rs` — move
`strip_code_fence` to `generation/mod.rs` and use it from both, rather than a second
copy), then validates **per question**: `kind` is `mcq` or `short`; an `mcq` has
`options` of exactly `MCQ_OPTIONS` non-empty strings and an `answer` that equals one of
them (after normalisation, so a trailing space is not a rejection); a `short` has
`options: None` and non-empty `key_points`. A violation is `GenerationError::Schema`
with the question's index in the message, so a retry's corrective message can name it.

`resolve_questions` mirrors `resolve_cards`: drop a question with an empty `prompt` or
`answer`, resolve `label` through `ContextLabels::chunk`, and record a miss in
`dropped_labels`.

```rust
/// The denominator is the *graded* attempts, not every attempt: a short answer the
/// student has not marked yet is not a wrong answer, and counting it as one would
/// make the score fall as they work through the quiz.

        rec("mcq", Some("s1"), Some(12), Some(true)),
        rec("mcq", Some("s1"), Some(12), Some(false)),
        rec("short", Some("s1"), Some(30), None), // not marked yet

    assert_eq!(summary.graded, 2);
    assert_eq!(summary.correct, 1);

/// Weakest first, and the questions whose label never resolved get their own bucket

        rec("mcq", Some("s1"), Some(12), Some(false)),
        rec("mcq", Some("s2"), Some(4), Some(true)),
        rec("short", None, None, Some(false)), // its label never resolved
    ];
    let summary = summarize(&records);

    let linked: Vec<_> = summary.topics.iter().filter(|t| t.source_id.is_some()).collect();
```

```rust
    let plan = user.plan();
    let month_start = util::local_month_start(&user.timezone, state.clock.as_ref());

    // The count, the charge and the reserving row commit together, because the limit
    // depends on the count: in separate transactions a second request reads a count
    // the first has not committed yet, and two concurrent requests both pass on the
    // last slot. The lock is the same key `credits::spend_in` takes below, so this
    // serialises quiz creation per account; it is transaction-scoped and re-entrant,
    // so the spend does not block on this same lock.
    let mut tx = state.pool.begin().await.map_err(…)?;
    sqlx::query("select pg_advisory_xact_lock(hashtext($1::text))")
        .bind(user.user_id.to_string())
        .execute(&mut *tx)
        .await
        .map_err(…)?;

    // This month's quizzes **plus** the ones still generating. The second term is what
    // makes the cap hold under concurrency: a quiz that is still generating has no
    // `quiz_questions` rows, so without it a burst of requests would each read zero
    // used. A `failed` quiz is excluded: its reservation was refunded, so it must not
    // keep consuming the allowance.
    let used: i64 = sqlx::query_scalar(
        "select count(*)::bigint from quizzes
          where user_id = $1 and deleted_at is null and created_at >= $2
            and status in ('ready', 'generating')",
    )
    .bind(user.user_id)
    .bind(month_start)
    .fetch_one(&mut *tx)
    .await
    .map_err(…)?;

    // One request creates exactly one quiz, so the request reserves 1.
    limits::enforce_batch(
        &state.config.plans,
        plan,
        state.config.plans.get(plan).quizzes_per_month,
        used,
        1,
        "quizzes",
    )?;

    let batches = (i64::from(body.count) + QUESTIONS_PER_BATCH - 1) / QUESTIONS_PER_BATCH;
    let cost = batches * state.config.plans.credits.quiz_10;
    let spent = credits::spend_in(&mut tx, &state, user.user_id, plan, GENERATE_ACTION, cost, [None, None]).await?;

    let (quiz_id, created_at): (Uuid, DateTime<Utc>) = sqlx::query_as(
        "insert into quizzes
            (user_id, workspace_id, title, difficulty, status, source_ids, requested_count,
             question_types, credits_spent, usage_event_id)
         values ($1, $2, $3, $4, 'generating', $5, $6, $7, $8, $9)
         returning id, created_at",
    )
    .bind(…)
    // `source_ids` is the deduplicated, ownership-checked list, exactly as the deck
    // route binds it: the job reads it back to build the prompt.
    .fetch_one(&mut *tx)
    .await
    .map_err(|error| {
        // A failed insert needs no refund by hand: the charge, the reservation and the
        // row are all in this transaction, so rolling back unspends the credit.
        AppError::Internal(anyhow::anyhow!("creating the quiz: {error}"))
    })?;

    tx.commit().await.map_err(…)?;
```

## Execution notes (Phase 5, as built)

Three things were found while building that the plan did not anticipate, and each is
recorded here rather than only in the code.

1. **`quiz_questions` had no `key_points` column, and the module's own schema
   requires it.** The spec's sketch omits it and `prompts/quiz.v1.md` documents it, so
   the first generation failed at the insert with `column "key_points" of relation
   "quiz_questions" does not exist`. A student marking their own short answer is shown
   the model answer *and* these points; "did I say what mattered" is not answerable
   from a bare answer sentence (A100).
2. **`quizzes` had no `source_ids` column, so the generation job had nothing to
   generate from.** The route would have accepted a request, charged for it, and
   failed the job with an empty prompt. Caught by writing the insert against the real
   schema rather than by running it (A100).
3. **Every question of one generation shares a `created_at` to the microsecond**, so
   ordering by `(created_at, id)` fell through to a random uuid and the quiz came back
   in a different order than the model wrote it. `idx` is now stored and the order
   comes from it (A100). A related ambiguity was found by a test: two attempts on one
   question can share an `answered_at`, so "the latest attempt" ordered by time alone
   was non-deterministic. A graded attempt now supersedes an ungraded one.

The plan's Task 4 also said to write the monthly-reservation test first, and that is
what happened: `a_quiz_still_generating_counts_against_the_monthly_limit` was written
against the not-yet-correct behaviour and passed, because the reservation was built
in from the start rather than added after a review found the hole.

### Roadmap gate 5, accessibility, on the quiz screen: PASS

Measured in a real browser (Chromium, 390x844 viewport, both `prefers-color-scheme`
values), not asserted.

- **(a) Keyboard only.** `Tab` reaches every control in order — the skip link, the

  `1`-`4` select an MCQ option without the mouse, gated on the question being

  already submitted. `Enter` submits from the focused button. A full quiz was taken,
  marked and finished by keyboard alone.
- **(b) Contrast, both themes.** Computed WCAG ratios from the rendered colours:
  question text 13.77 dark / 19.03 light, option labels the same, the submit button
  16.72 / 19.03, the `meta` line 7.41 / 5.06, the legend 6.10 / 5.43, the verdict word

- **(c) 44px targets.** Every option row is exactly 44px high and the submit button
  44px, at phone width. Measured, not assumed.
- **(d) No state by colour alone.** The verdict is a word: "Correct" or "Not correct.
  The answer is: <option>". The status chip carries "Generating" / "Ready" /

- **(e) 200% text scale on 390px.** **This found a real defect.** The `fieldset` around

  elements, zero clipped elements, no horizontal page overflow, panel scroll width
  equal to its client width.

## Self-Review

- **Spec coverage:** the spec's `## Quiz` section asks for MCQ and short answer,
  configurable count and difficulty, strict JSON, an explanation and a linked chunk per
  question, append-only attempts, and a score plus a weak-topic summary grouped by
  source/page. Every one of those is a task above. The route list
  (`POST /workspaces/:id/quizzes`, `GET /quizzes/:id`, `POST /quizzes/:id/attempts`,
  `GET /quizzes/:id/results`) is implemented as written, plus one list route (A95).
- **Placeholders:** none. The two genuine unknowns are pinned rather than waved at:
  how a short answer is graded (A90) and what `quizzes_per_month` counts (A94). Both are
  choices the spec does not make, and both are recorded where the next phase can find
  them.
- **The bug this plan exists to avoid:** the monthly reservation. Phase 4 shipped a cap
  that counted only rows that existed, which meant a deck still generating counted as
  zero; the cap could be exceeded by asking twice in a row, and the test that proved it
  had to be written afterwards. Task 4 writes that test first, and the count includes
  `status = 'generating'` from the start.
- **Type consistency:** `ResolvedQuestion`, `QuizParseOutcome`, `AnswerRecord`,
  `TopicRow` and `QuizSummary` are each defined once in core and referenced by name in
  the server and the SPA. `GenerationError` and `is_retryable` are reused, not
  redefined. `ModuleId::QuizV1` is the only new prompt identity.
- **Open item:** B1 (QRIS gateway docs) is still needed at Phase 13, not before.
