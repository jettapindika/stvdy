# Assumptions & Open Decisions

Everything below was decided because the spec left it open. Disagree with any row and the plan changes; rows marked **BLOCKER** must be resolved before the phase that needs them.

## Blockers

| # | Blocker | Needed by | Blocks public launch? | Workaround until resolved |
|---|---------|-----------|----------------------|---------------------------|
| B1 | QRIS gateway identity + API docs (spec says `GATEWAY = <FILL IN>`): base URL, auth scheme, invoice-create response fields, status-query shape, callback signature scheme, fee rates | Phase 13 | **Yes. Hard.** No revenue is possible without it, and the free tier is a pure cost centre (A41). Also: the underlying **PJP must be identified**, since a self-hosted gateway still settles through a BI-licensed provider, and perorangan onboarding (KTP + NPWP + matching bank account + a working platform with visible prices) is itself a lead-time item. | Implement `PaymentProvider` + `qris_gateway` against a documented internal contract; every gateway-specific value read from env (`QRIS_BASE_URL`, `QRIS_API_KEY`, `QRIS_CALLBACK_TOKEN`, `QRIS_SIGNATURE_SCHEME`, `QRIS_FEE_PERCENT`). | B2 | Tax/PPN treatment and store privacy-label text | Phase 15 | **Yes. Legal.** Public launch needs invoices that are correct and a privacy notice that is true (UU PDP). | ToS/privacy placeholder pages; no tax line items on invoices; documented in `docs/RELEASE.md`. |
| B3 | Email sending credentials (SMTP host/user/pass) and From address | Phase 1 | **Yes. Operational.** Email verification gates every AI action (A43), so without SMTP no account can spend, and no user can be onboarded. | Dev sink: verification/reminder emails written to stdout + `var/mail/` files. Provider swap is config-only. |

**Reading this table for a launch decision:** "Needed by" is the phase that *implements* against the blocker; "Blocks public launch?" is when it stops being tolerable. B1, B2 and B3 all block a public launch even though they are filed under Phases 13, 15 and 1 respectively. So they must be started in parallel with development, not discovered at their phase. The remaining launch prerequisites that are **not** blockers because they are fully specified in-repo: the abuse controls (A43), the licensing artifacts (A44), the hosting decision (A45), and the operations sections in `docs/RELEASE.md`.

Verified in a browser: `{{count}}` resolves inside stretched copy (`"Báášééd óóñ 1 šóóúúrçé"`, `"1 çhúúúñk"`) with no literal `{{…}}` anywhere on the page. | Accenting a placeholder's letters (`{{count}}` → `{{çóúñt}}`) stops i18next resolving it, and the pseudo-locale render would show a literal `{{çóúñt}}`, which reads as an app bug rather than the layout problem the pseudo-locale exists to expose. Measuring the length on the text rather than the whole string is what keeps the guarantee meaningful once placeholders are exempt. |
| A119 | A cheatsheet has no monthly cap; it is bounded by credits only | `POST /workspaces/:id/cheatsheets` charges `report_section` (6) and writes its reserving row in one transaction, but does not count against `reports_per_month`. `docs/API.md` § Cheatsheets states it. | `config/plans.toml` has no cheatsheet allowance. Counting a cheatsheet against `reports_per_month` would be a policy the matrix does not state, and the roadmap's cost table prices a cheatsheet as the report's section rather than as a separately limited feature. The cap that does exist (credits) is the one the matrix states, and it is enforced on the same spend path as every other generator. |
| A120 | A report is priced as outline (3) + section (6) per section, and a cheatsheet as one section (6) | `credits::spend_in` is called once for the outline (`report_outline`), once per section (`report_section`), and once for a cheatsheet (`report_section`). The SPA reads the same two numbers from `config/plans.toml` through `app/src/features/billing/plans.ts`. | The roadmap's cost table has `report_outline = 3` and `report_section = 6` and no `cheatsheet` key, and it says explicitly that where the matrix has no key the outline+section pair is what the thing costs rather than a price invented in code. Charging per section is also what makes "regenerate section 3 without paying for the whole report again" true, which the spec's step 2 asks for. |
| A121 | `reports` gains generation columns and three the section job cannot work without | `0023_report_generation.sql` adds `status`, `error`, `credits_spent`, `usage_event_id`, `source_ids`, `style`, `length`, `sections_md` and `generating_index`. `docs/API.md` names every one that reaches a payload. | `status`/`error`/`credits_spent`/`usage_event_id` are the bookkeeping every generator carries (the refund path needs the last two). `source_ids` and the two prompt settings are required because a section call is a **separate prompt** from the outline call and the job runs after the request returned: without them the job has no chunks and no `{{style}}`/`{{length}}`, and every section would fail with an empty prompt after the student had paid for it. `sections_md` is stored rather than derived from `body_md` because splitting Markdown on its headings cannot tell a section boundary from a `## ` line the model wrote inside a section. |
| A122 | A report's section texts are index-aligned with its outline, and an edit re-aligns them by heading | `sections_md` is a JSON array parallel to `outline.sections`; `PATCH /reports/:id` carries a section's text across only when its heading appears exactly once in both the old and the new outline. Tested in `crates/server/src/reports/routes.rs` (`a_reordered_outline_keeps_each_sections_text`, `a_renamed_section_is_unwritten_and_a_deleted_one_is_dropped`, `a_duplicated_heading_does_not_inherit_a_text`). | Index alignment alone would re-label a section's prose with its neighbour's heading after a reorder, and a rename would keep text written for a different purpose. Both failures reach a printed report with nothing on the page to say so, so an ambiguous heading loses that section's text instead — which the student can regenerate for 6 credits. |
| A123 | The report PDF is printed from Markdown through a server-side subset renderer, and `pdf` joins the report export | `crates/server/src/reports/render.rs` converts headings, paragraphs, lists, block quotes, inline code, bold, italic and `[n]` labels into the markup of `templates/report.v1.html`; everything else is escaped and shown literally. | The spec says `.md` first with PDF/DOCX "later, gated by plan", and the phase's gate is the export menu with its plan-locked variants — which is only real if a plan can actually get a PDF. A full Markdown implementation would be a parser plus a CommonMark conformance suite plus a sanitiser, and it is not a second engine to keep in step with the client's. The subset is what the section prompt asks for, and it escapes every character before it writes any tag. |
| A124 | `GET /reports/:id` returns a `sections` array, and `GET /cheatsheets/:id/html` returns the document itself | `sections: [{ heading, body_md: string-or-null, generating, error }]`, derived from the stored outline joined with `sections_md`. The HTML route answers `text/html; charset=utf-8`. Both are named in `docs/API.md`. | Per-section progress is read from a server flag because the job outlives the tab that started it: a client-side pending mutation would show "idle" for work still running on the other device. The HTML route is a document because the preview frame consumes it as `srcdoc` and the free plan's remedy for a withheld PDF is to print it from a browser; neither works through a JSON envelope. |
| A125 | `GET /workspaces/:id/reports` and `GET /workspaces/:id/cheatsheets` exist beyond the spec's route list | Both are lists, newest first, tombstones excluded, scoped by `user_id` and workspace. | Without them a report or a cheatsheet is unreachable after a page reload and the Studio panel cannot poll the ones still generating. They are the two routes the decks and quizzes phases already added for the same reason, named the same way. |
| A126 | The cheatsheet's stored artifact is a JSON envelope of the reply text plus its label map | `blocks_key` holds `{"blocks": "<fence-stripped reply>", "labels": [{"label","chunk_id","source_id","page"}]}`. `StoredDocument` in `crates/server/src/cheatsheets/generate.rs`. | The reply text is stored verbatim because it is the canonical form `parse_blocks` reads, and `Blocks` is `Deserialize`-only on purpose (the renderer never writes one), so re-encoding it would need a second statement of the schema in the server. The labels travel with it because they are request-scoped and cannot be recovered from the blocks: a re-render that re-derived them would silently drop every citation marker once a source was deleted or re-indexed, producing a different document from the one the student paid for with nothing on the page to say so. |
| A127 | The cover's `generated_at` is the row's `created_at`, not a clock reading at render time | `cheatsheets::generate::cover_for` formats `cheatsheets.created_at` in the owner's IANA zone. `crates/server/tests/cheatsheets.rs::re_rendering_is_identical_and_calls_no_model` asserts the re-rendered HTML is byte-identical. | A re-render must produce the same document, and a clock in the cover would change it every time while the content stayed the same — the exact regression the purity property exists to prevent. `created_at` is when the student asked for the document, which is what the cover's "Dibuat" means anyway. |
| A128 | The Chromium renderer waits for the template's `data-math-ready` sentinel, with a bounded deadline | `Renderer::render_within(html, header, timeout_ms)` polls `document.documentElement.dataset.mathReady` inside the page and fails with `RenderError::MathNotReady` on any value other than `"1"` or on no value at all. `MATH_READY_TIMEOUT_MS` is 30s in production; both failure paths are tested in `crates/server/tests/pdf.rs`. | The template documents the sentinel and the failure it prevents: a KaTeX that did not load renders the maths as literal `$x$`, the page looks plausible, the PDF is produced, and nobody notices until a student prints it. The deadline makes the guard safe in the other direction — a template that never sets the attribute must fail the job rather than hang the worker on a promise that never settles. |
| A129 | `CHROME_PATH` is the first place the renderer looks, and the tests resolve Chrome the same way | `crates/server/src/render/chrome.rs::find_executable` reads `CHROME_PATH`, then probes `/Applications/Google Chrome.app/Contents/MacOS/Google Chrome`, `/usr/bin/google-chrome`, `/usr/bin/chromium`, `/usr/bin/chromium-browser`. `crates/server/tests/pdf.rs` calls it rather than re-implementing the list. | A test that resolved Chrome by a different rule than the server would prove something about the test. The image's pinned build is named by `CHROME_PATH` (`docs/RELEASE.md`), and the probe list is only for a developer's machine, where the vendor installer does not put Chrome on `PATH`. |
| A130 | The Chromium renderer is optional, and its absence is a supported state rather than a startup failure | `AppState.renderer: Option<Arc<Renderer>>`; `Providers::build` launches it at boot and logs an error if it cannot, leaving the field `None`. Without a renderer the cheatsheet pipeline still stores the blocks and the HTML and the cheatsheet is `ready`; `GET /cheatsheets/:id/pdf` answers 409 `conflict` until a print exists, and a report's `format=pdf` export answers 502 `provider_error`. `render_cheatsheet_pdf` fails **permanently** (no retry will install a browser) and records the reason in `error` without touching `status` or `credits_spent`. | A deployment without a browser must not be able to destroy a paid generation, and it must not spend five attempts with backoff to be told the same thing. The document is the blocks; the print is the one step that needs Chromium, and `POST /cheatsheets/:id/re-render` is the recovery path once one is available. |
| A131 | `RefundTarget` gains `Report` and `Cheatsheet` | `crates/server/src/credits.rs` carries one SQL arm per target; `main.rs` sweeps all four at boot. `crates/server/tests/reports.rs::a_charge_left_pending_by_a_failed_refund_is_recovered` exercises it and asserts a second sweep recovers nothing. | Both new generators have the same failure path as a deck and a quiz: a ledger insert that cannot be written leaves the row terminal with `credits_spent > 0`, which is exactly "charged and not delivered, refund pending". Without the two variants that state would be permanent and invisible — the row reads `failed`, so nothing else would ever look at it again. The sequence is shared rather than copied because it is subtle enough that a second copy would be a second place to get it wrong. |

## Local development environment

Not a product decision, but it changes what a contributor sees, so it is recorded rather than left implicit.

| | Spec / CI | This workstation |
|---|---|---|
| Postgres | 16 (`pgvector/pgvector:pg16` in `docker-compose.yml` and the CI service) | 17.11 (Homebrew `postgresql@17`) |
| pgvector | bundled in the image | 0.8.6, installed |
| Port | 5432 | 5432 |
| Role | `postgres` / `postgres` | `mac`, trust auth |

Consequences worth knowing:

- **A local Postgres on 5432 blocks `just db-up`.** Homebrew's `postgresql@17` holds the port, so `docker compose up postgres` cannot bind it. Either stop it (`brew services stop postgresql@17`) or point `DATABASE_URL` at it, which is what `.env` does here.
- **Local is 17, CI is 16.** Migrations are written to run on 16 and verified on both, but a version-specific feature used locally could pass here and fail in CI. When in doubt, trust the CI service's result.
- **CI is authoritative.** The `test` job runs against `pgvector/pgvector:pg16`, which is the pinned version; local 17 is a convenience, not the target.
- Docker Desktop must be running for the compose services; `docker ps` failing on a missing socket means it is not.

## Schema deviations from the spec (intentional, small)

| Change | Why |
|--------|-----|
| `users.password_hash` becomes **nullable**, plus `google_sub text unique` and `email_verified_at timestamptz` | A48. Google login creates users with no password, and the spec's `password_hash text not null` would make that impossible. `google_sub` is the stable Google identifier and is the **only** thing that may be trusted for account linking; `email` alone is not, because a Google account's email can change and an unverified match would be an account-takeover path. `email_verified_at` records *when* verification happened, which the A43 "verified email required before any AI action" rule needs as a timestamp rather than the existing boolean alone. |
| `users.is_admin boolean not null default false` | A7. Admin routes need an authority. |
| `events.task_id` gets `references tasks(id) on delete set null` | Spec left it an unconstrained uuid; a link without a FK drifts. **Ordering consequence:** `0012_tasks_*` must run before `0013_calendar_events`, or a fresh `sqlx migrate run` fails. |
| `jobs.dedupe_key text` + `unique` index (nullable) | A10. Singleton scheduled jobs (`monthly_grant`, `compact_change_log`, `poll_payment`) must not double-run across restarts or instances; a duplicate `monthly_grant` double-grants credits. |
| `pending_actions` gains `user_id`/`updated_at`/`deleted_at` + both sync triggers | The spec's DDL omits the `-- +sync` marker on `pending_actions`, but it is a synced entity: `Entity::PendingAction` (rank 16) requires it, and the spec says pending actions must be "visible and confirmable from any signed-in device". |
| New table `report_revisions` | The spec's conflict rules require that when a long text (`reports.body_md`) is edited on two devices, the losing version is kept "as a recoverable copy". There is no table for it in the spec's DDL. It is server-side recovery data: no triggers, not synced, like billing internals. |
| `chunks.embedding` dimension is a single migration constant (default `768`) | A2. Must equal the configured embedder dimension; one place to change. |
| `chunks` gains an `embedder text not null` column, and the dedupe index becomes a **non-unique** `index on chunks (embedder, content_hash)` replacing the spec's plain `content_hash` index | Two reasons. (1) The spec's dedupe rule ("skip re-embedding chunks whose content_hash already exists") would silently reuse vectors from a *different* embedding model after a provider switch, leaving mixed vector spaces in one table and corrupting retrieval. So the lookup must be keyed on embedder identity. (2) It must **not** be a unique constraint: `chunks` has no `user_id` (it is scoped through `source_id → sources.workspace_id → workspaces.user_id`), so uniqueness would be global across all accounts. The first user to upload a widely-shared textbook would make ingestion *fail* for every other user who uploads the same file, and the error would leak content existence across tenants. `source_id` is `not null`, so chunks can never be shared rows anyway. Dedupe is implemented as a lookup that copies the existing embedding into the new row, scoped to the same user by joining through `sources`/`workspaces`. |
| `change_log.origin_device_id` is filled from `current_setting('app.device_id')` set per transaction | Avoids adding a device column to every sync table just for the log. |
| `log_change()` / `log_change_by_user()` take `pg_advisory_xact_lock(hashtext(user_id::text))` before inserting | Correctness, not tuning: `seq` is assigned by `nextval()` at insert time but rows become visible at commit time, so without the lock a pull cursor can permanently skip a lower seq that committed later. See roadmap § Sync protocol. |
| New table `cheatsheets` (+sync metadata) | The spec has no cheatsheet entity, but the print-PDF feature needs one to persist a generated document. Stores `title`, `scope`, `exam_date`, `depth`, `source_ids`, `status`, `error` and the object-storage keys for the rendered HTML and PDF. The rendered artifacts live in object storage (they are large and are not edited on-device), so only metadata syncs. |
| Citation format: numeric labels, not `[[chunk:<uuid>]]` | The spec's § Retrieval and chat states the same numeric-label rule; what this row pins is the implementation detail. Sending raw UUIDs costs ~40 tokens per citation and lets a model fabricate a plausible-looking UUID; numeric labels are cheaper and an unknown label is trivially rejected against the context the server sent. `crates/core/src/citations.rs` is therefore a label→chunk resolver. The structured `messages.citations` form from the spec is unchanged. |
| `usage_events` gains `prompt_version text` | The prompt version that produced each action, so a quality or cost regression can be attributed to a prompt change rather than guessed at (A38). Nullable, because not every action calls a model. |
| New table `email_verification_tokens` | The spec's DDL has no token store, and `/auth/verify-email` plus A48's "a Google-only account must verify its email before setting a password" rule both need one. Holds `token_hash` (SHA-256, never the token), `expires_at` and `used_at`, so a link is single-use and expiring. **Not `+sync`**: a verification token is a credential, and a client must never see or replay one through the change log. Appended as `0018` after `0017_sync_triggers.sql` without touching that migration's trigger array. |
| New table `login_tickets` | A48's callback runs in the system browser and must hand the app something. Putting an access or refresh token in the deep link would write a credential into browser history, referrer logs and the OS URL handler, so the callback redirects with an opaque single-use ticket and the app exchanges it over HTTPS for the real pair. Holds `ticket_hash` only, plus the declared device, a short `expires_at` and `used_at`. **Not `+sync`** for the same reason as above. |
| `crates/server/tests/schema.rs` `documented` list carries both new tables | That test's contract is "anything not in the spec's DDL must be a documented deviation", so a table added without a row here fails it. Both are listed in the test and in this table. |
| `jobs.kind` gains `generate_cheatsheet`, `render_cheatsheet_pdf` | Split so a PDF-rendering failure does not discard a successfully generated cheatsheet; the HTML is still usable and printable from a browser. |
| New table `search_cache`, plus `usage_events.cache_hit`/`search_tier`/`unresponsive_engines` | A40. The cache is **global, not per-user**: a query string carries no user data, so a per-user table would multiply storage by the user count for no benefit. `key` is `sha256(normalized_query \| provider \| max_results)` from `crates/core/src/search/normalize.rs`; `expires_at` carries the TTL and has its own index for the purge job. The three `usage_events` columns are what make the accounting honest: `cache_hit` keeps a free request visible in the margin report, `search_tier` names what actually answered, and `unresponsive_engines` records SearXNG's own list of engines that failed so silent degradation of the free path is a row rather than a user's complaint. **Not `+sync`**: server-side cost control, no client-visible entity. |
