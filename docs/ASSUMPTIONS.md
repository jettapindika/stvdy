# Assumptions & Open Decisions

Everything below was decided because the spec left it open. Disagree with any row and the plan changes; rows marked **BLOCKER** must be resolved before the phase that needs them.

## Blockers

| # | Blocker | Needed by | Blocks public launch? | Workaround until resolved |
|---|---------|-----------|----------------------|---------------------------|
| B1 | QRIS gateway identity + API docs (spec says `GATEWAY = <FILL IN>`): base URL, auth scheme, invoice-create response fields, status-query shape, callback signature scheme, fee rates | Phase 13 | **Yes. Hard.** No revenue is possible without it, and the free tier is a pure cost centre (A41). Also: the underlying **PJP must be identified**, since a self-hosted gateway still settles through a BI-licensed provider, and perorangan onboarding (KTP + NPWP + matching bank account + a working platform with visible prices) is itself a lead-time item. | Implement `PaymentProvider` + `qris_gateway` against a documented internal contract; every gateway-specific value read from env (`QRIS_BASE_URL`, `QRIS_API_KEY`, `QRIS_CALLBACK_TOKEN`, `QRIS_SIGNATURE_SCHEME`, `QRIS_FEE_PERCENT`). | B2 | Tax/PPN treatment and store privacy-label text | Phase 15 | **Yes. Legal.** Public launch needs invoices that are correct and a privacy notice that is true (UU PDP). | ToS/privacy placeholder pages; no tax line items on invoices; documented in `docs/RELEASE.md`. |
| B3 | Email sending credentials (SMTP host/user/pass) and From address | Phase 1 | **Yes. Operational.** Email verification gates every AI action (A43), so without SMTP no account can spend, and no user can be onboarded. | Dev sink: verification/reminder emails written to stdout + `var/mail/` files. Provider swap is config-only. |

**Reading this table for a launch decision:** "Needed by" is the phase that *implements* against the blocker; "Blocks public launch?" is when it stops being tolerable. B1, B2 and B3 all block a public launch even though they are filed under Phases 13, 15 and 1 respectively. So they must be started in parallel with development, not discovered at their phase. The remaining launch prerequisites that are **not** blockers because they are fully specified in-repo: the abuse controls (A43), the licensing artifacts (A44), the hosting decision (A45), and the operations sections in `docs/RELEASE.md`.

| A42 | Client is untrusted; the server is the only enforcement point | The client binary is treated as **attacker-controlled** in every security decision. ## Local development environment

Not a product decision, but it changes what a contributor sees, so it is recorded rather than left implicit.

| | Spec / CI | This workstation |
|---|---|---|
| Postgres | 16 (`pgvector/pgvector:pg16` in `docker-compose.yml` and the CI service) | 17.11 (Homebrew `postgresql@17`) |
| pgvector | bundled in the image | 0.8.6, installed |
| Port | 5432 | 5432 |
| Role | `postgres` / `postgres` | `mac`, trust auth |

Consequences worth knowing:

- **A local Postgres on 5432 blocks `just db-up`.** Homebrew's `postgresql@17` holds the port, so `docker compose up postgres` cannot bind it. Either stop it (`brew services stop postgresql@17`) or point `DATABASE_URL` at it, which is what `.env` does here.
- **Local is 17, CI is 16.** Migrations are written to run on 16 and verified on both, but a version-specific feature used locally could pass here and fail in CI. When in doubt, trust the CI service's result.
- **CI is authoritative.** The `test` job runs against `pgvector/pgvector:pg16`, which is the pinned version; local 17 is a convenience, not the target.
- Docker Desktop must be running for the compose services; `docker ps` failing on a missing socket means it is not.

## Schema deviations from the spec (intentional, small)

| Change | Why |
|--------|-----|
| `users.password_hash` becomes **nullable**, plus `google_sub text unique` and `email_verified_at timestamptz` | A48. Google login creates users with no password, and the spec's `password_hash text not null` would make that impossible. `google_sub` is the stable Google identifier and is the **only** thing that may be trusted for account linking; `email` alone is not, because a Google account's email can change and an unverified match would be an account-takeover path. `email_verified_at` records *when* verification happened, which the A43 "verified email required before any AI action" rule needs as a timestamp rather than the existing boolean alone. |
| `users.is_admin boolean not null default false` | A7. Admin routes need an authority. |
| `events.task_id` gets `references tasks(id) on delete set null` | Spec left it an unconstrained uuid; a link without a FK drifts. **Ordering consequence:** `0012_tasks_*` must run before `0013_calendar_events`, or a fresh `sqlx migrate run` fails. |
| `jobs.dedupe_key text` + `unique` index (nullable) | A10. Singleton scheduled jobs (`monthly_grant`, `compact_change_log`, `poll_payment`) must not double-run across restarts or instances; a duplicate `monthly_grant` double-grants credits. |
| `pending_actions` gains `user_id`/`updated_at`/`deleted_at` + both sync triggers | The spec's DDL omits the `-- +sync` marker on `pending_actions`, but it is a synced entity: `Entity::PendingAction` (rank 16) requires it, and the spec says pending actions must be "visible and confirmable from any signed-in device". |
| New table `report_revisions` | The spec's conflict rules require that when a long text (`reports.body_md`) is edited on two devices, the losing version is kept "as a recoverable copy". There is no table for it in the spec's DDL. It is server-side recovery data: no triggers, not synced, like billing internals. |
| `chunks.embedding` dimension is a single migration constant (default `768`) | A2. Must equal the configured embedder dimension; one place to change. |
| `chunks` gains an `embedder text not null` column, and the dedupe index becomes a **non-unique** `index on chunks (embedder, content_hash)` replacing the spec's plain `content_hash` index | Two reasons. (1) The spec's dedupe rule ("skip re-embedding chunks whose content_hash already exists") would silently reuse vectors from a *different* embedding model after a provider switch, leaving mixed vector spaces in one table and corrupting retrieval. So the lookup must be keyed on embedder identity. (2) It must **not** be a unique constraint: `chunks` has no `user_id` (it is scoped through `source_id → sources.workspace_id → workspaces.user_id`), so uniqueness would be global across all accounts. The first user to upload a widely-shared textbook would make ingestion *fail* for every other user who uploads the same file, and the error would leak content existence across tenants. `source_id` is `not null`, so chunks can never be shared rows anyway. Dedupe is implemented as a lookup that copies the existing embedding into the new row, scoped to the same user by joining through `sources`/`workspaces`. |
| `change_log.origin_device_id` is filled from `current_setting('app.device_id')` set per transaction | Avoids adding a device column to every sync table just for the log. |
| `log_change()` / `log_change_by_user()` take `pg_advisory_xact_lock(hashtext(user_id::text))` before inserting | Correctness, not tuning: `seq` is assigned by `nextval()` at insert time but rows become visible at commit time, so without the lock a pull cursor can permanently skip a lower seq that committed later. See roadmap § Sync protocol. |
| New table `cheatsheets` (+sync metadata) | The spec has no cheatsheet entity, but the print-PDF feature needs one to persist a generated document. Stores `title`, `scope`, `exam_date`, `depth`, `source_ids`, `status`, `error` and the object-storage keys for the rendered HTML and PDF. The rendered artifacts live in object storage (they are large and are not edited on-device), so only metadata syncs. |
| Citation format: numeric labels, not `[[chunk:<uuid>]]` | `docs/SPEC.md` § Retrieval says the model must cite by chunk ID. Sending raw UUIDs costs ~40 tokens per citation and lets a model fabricate a plausible-looking UUID; numeric labels are cheaper and an unknown label is trivially rejected against the context the server sent. `crates/core/src/citations.rs` is therefore a label→chunk resolver. The structured `messages.citations` form from the spec is unchanged. |
| `usage_events` gains `prompt_version text` | The prompt version that produced each action, so a quality or cost regression can be attributed to a prompt change rather than guessed at (A38). Nullable, because not every action calls a model. |
| New table `email_verification_tokens` | The spec's DDL has no token store, and `/auth/verify-email` plus A48's "a Google-only account must verify its email before setting a password" rule both need one. Holds `token_hash` (SHA-256, never the token), `expires_at` and `used_at`, so a link is single-use and expiring. **Not `+sync`**: a verification token is a credential, and a client must never see or replay one through the change log. Appended as `0018` after `0017_sync_triggers.sql` without touching that migration's trigger array. |
| New table `login_tickets` | A48's callback runs in the system browser and must hand the app something. Putting an access or refresh token in the deep link would write a credential into browser history, referrer logs and the OS URL handler, so the callback redirects with an opaque single-use ticket and the app exchanges it over HTTPS for the real pair. Holds `ticket_hash` only, plus the declared device, a short `expires_at` and `used_at`. **Not `+sync`** for the same reason as above. |
| `crates/server/tests/schema.rs` `documented` list carries both new tables | That test's contract is "anything not in the spec's DDL must be a documented deviation", so a table added without a row here fails it. Both are listed in the test and in this table. |
| `jobs.kind` gains `generate_cheatsheet`, `render_cheatsheet_pdf` | Split so a PDF-rendering failure does not discard a successfully generated cheatsheet; the HTML is still usable and printable from a browser. |

## Crate-list deviations

| Spec says | Plan uses | Why |
|-----------|-----------|-----|
| `ical` for parsing ICS | `icalendar` 0.17.14 for **both** parse and generate; `rrule` 0.14 for recurrence | `ical` 0.11 is dormant (last release Mar 2024); `icalendar` is actively maintained and already required for generation. Recurrence iteration must be bounded (`all(limit)` + check `limited`). |
| `pdfium-render` **or** `lopdf` | `pdfium-render` 0.9.4 primary (native `libpdfium` baked into the server image, extraction behind one mutex since pdfium is not thread-safe), `lopdf` 0.45 for page count/metadata + fallback | pdfium has the only reliable text+page fidelity; serializing extraction is fine because ingestion is a background job. |
| `zip` + `xml` for PPTX/DOCX | `zip` 9.0.1 (`default-features = false, features = ["deflate"]`) + `quick-xml` 0.42, walking `ppt/slides/slideN.xml` `<a:t>` runs and `word/document.xml` `<w:t>` runs | No mature dedicated PPTX/DOCX text extractor in Rust; both formats need zip-slip and decompressed-size guards anyway. |
| "S3-compatible" client | `aws-sdk-s3` 1.152 with `force_path_style(true)`, `BehaviorVersion::latest()`, `request_checksum_calculation(WhenRequired)` | Required for MinIO/self-hosted endpoints; the checksum default breaks some S3-compatible servers. |
| `oauth2` + `reqwest` | `oauth2` 5.0.0 (pulls its own `reqwest` 0.12) alongside our `reqwest` 0.13.5 | oauth2 5 pins reqwest 0.12; two versions coexist. Accepted, not fought. |

## Out of scope (confirmed from spec)

Apple IAP, Google Play Billing, auto-renewing billing, audio overviews, lecture recording/transcription, realtime collaboration, Mac App Store / Microsoft Store, Linux, widgets/watch apps, OCR/camera scanning, on-device LLMs, offline chat/generation/uploads, multiple chat threads per workspace, non-Google OAuth, LMS integrations, browser extension, Stripe/international payments.
