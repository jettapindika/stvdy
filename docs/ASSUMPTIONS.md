# Assumptions & Open Decisions

Everything below was decided because the spec left it open. Disagree with any row and the plan changes; rows marked **BLOCKER** must be resolved before the phase that needs them.

**Reading this table for a launch decision:** "Needed by" is the phase that *implements* against the blocker; "Blocks public launch?" is when it stops being tolerable. B1, B2 and B3 all block a public launch even though they are filed under Phases 13, 15 and 1 respectively. So they must be started in parallel with development, not discovered at their phase. The remaining launch prerequisites that are **not** blockers because they are fully specified in-repo: the abuse controls (A43), the licensing artifacts (A44), the hosting decision (A45), and the operations sections in `docs/RELEASE.md`.

| A42 | Client is untrusted; the server is the only enforcement point | The client binary is treated as **attacker-controlled** in every security decision. Nothing that costs money, grants access, or mutates server-owned state may be decided on the device. Concretely: (1) clients never hold provider keys (`docs/SPEC.md` § PLATFORMS AND ARCHITECTURE); (2) `POST /sync/push` accepts exactly **six** entities and rejects the rest with `read_only_entity` (roadmap § Sync protocol); (3) derived fields (`flashcards.ease/interval/due`) are rejected on push; (4) entitlements are checked **per mutation** and per handler; (5) the JWT deliberately does **not** carry the plan (A22), so editing it grants nothing; (6) checkout is refused server-side for `platform in (ios, android)` (A24), so the client-embedded `billing_policy.toml` is defense-in-depth and never the control; (7) citation labels are validated against the context the server actually sent (A17). **Consequence, and the honest limit:** on desktop the binary is patchable and always will be. | A355 | Scope | **Account deletion and the data export ship, and A160 is honoured rather than standing.** `DELETE /account` marks `users.deleted_at`, revokes every credential, cancels the account's jobs and schedules `purge_deleted_accounts` at `deleted_at + ACCOUNT_DELETION_GRACE_DAYS`; `GET /account/export` answers JSON, Markdown and ICS. | A355a | Scope | **What the purge deletes, and what it keeps, is a per-table-group mapping rather than a cascade.** Deleted: `workspaces`, `sources`, `chunks` (cascade), `messages`, `decks`, `flashcards`, `flashcard_reviews`, `quizzes`, `quiz_questions`, `quiz_attempts`, `reports`, `report_revisions`, `cheatsheets`, `tasks`, `goals`, `study_sessions`, `events`, `plan_proposals`, `syllabus_drafts`, `pending_actions`, `reminders` (+ `reminder_deliveries` by cascade), `calendar_connections`, `user_settings`, `user_api_keys`, `devices` (+ `push_tokens` by cascade), `auth_sessions`, `email_verification_tokens`, `login_tickets`, `mutation_log`, `change_log_watermark`. | A355b | Scope | **`GET /account/export` is bounded, not streamed: `EXPORT_MAX_ROWS = 5000` per collection, with the truncated collections named in the document.** | The alternative is a chunked writer over twenty-seven queries, which buys a response shape neither client reads — both hand the bytes straight to a file — at the cost of a second streaming path to get right. A bound is also the honest choice: it lets the document *say* what was cut, which a stream cannot. 5,000 rows is a few megabytes of JSON for the largest table this product writes, which a phone can hold. | A230 | The feed's `UID` is `<events.id>@stvdy.app` and its `SEQUENCE` is derived from `(created_at, updated_at)`, not from a clock reading | `sequence = if updated_at > created_at { (updated_at - created_at).num_seconds().max(1) } else { 0 }`, with `DTSTAMP`/`LAST-MODIFIED` from `updated_at`. A feed is a cache the client owns: a client that caches on `UID` and finds no `SEQUENCE` has no signal an event changed, so an edited title is invisible forever, per client. *Stated limitation:* two edits inside one second produce the same `SEQUENCE`, because both are second-granular. |

| A232 | Expansion is bounded twice and truncation is recorded | `MAX_OCCURRENCES = 500`, `HORIZON_DAYS = 180`. The set asks for **one more than it keeps** and reports `truncated` when more were available. A truncated expansion writes `calendar_connections.error = 'recurrence_truncated'` and keeps every occurrence it read. **Measured against `rrule` 0.14.0:** `collect_with_error` ends with `was_limited \|\| limit == list.len()`, so `all(500)` on a rule with exactly 500 occurrences reports `limited == true` — a rule with no more to give recorded as truncated, a connection that looks broken while it is fine. A second copy of an AES-GCM `state` codec is a second place to get nonce handling wrong. |
| A236 | `sync_token` is the only sync cursor, and the mode is recorded | `calendar_connections.sync_token` holds Google's `nextSyncToken`; `last_sync_was_full boolean not null default true` records which mode the last pass ran in, and a `410 Gone` clears `sync_token` so the **next** pass is a full listing. The screen shows the error beside the connection, which is gate 7. |

## Local development environment

Not a product decision, but it changes what a contributor sees, so it is recorded rather than left implicit.

| | Spec / CI | This workstation |
|---|---|---|
| Postgres | 16 (`pgvector/pgvector:pg16` in `docker-compose.yml` and the CI service) | 17.11 (Homebrew `postgresql@17`) |
| pgvector | bundled in the image | 0.8.6, installed |
| Port | 5432 | 5432 |
| Role | `postgres` / `postgres` | `mac`, trust auth |

Consequences worth knowing:

- **A local Postgres on 5432 blocks `just db-up`.** Homebrew's `postgresql@17` holds the port, so `docker compose up postgres` cannot bind it. Either stop it (`brew services stop postgresql@17`) or point `DATABASE_URL` at it, which is what `.env` does here.
- **Local is 17, CI is 16.** Migrations are written to run on 16 and verified on both, but a version-specific feature used locally could pass here and fail in CI. When in doubt, trust the CI service's result.
- **CI is authoritative.** The `test` job runs against `pgvector/pgvector:pg16`, which is the pinned version; local 17 is a convenience, not the target.
- Docker Desktop must be running for the compose services; `docker ps` failing on a missing socket means it is not.
- **`GRACE_PERIOD_DAYS`** defaults to `3` (`crates/server/src/config.rs`, `get_i64(&get, "GRACE_PERIOD_DAYS", 3)`), which is the spec's "3-day grace period (configurable)". It is read by the `reset_counters` rollover, which marks a `grace` subscription `expired` once `current_period_end + grace_period_days <= now()`. It is the only knob this phase adds to `.env.example` beyond the config keys above.
- **`SOFFICE_BIN` is unset on this workstation** (no LibreOffice installed), so DOCX/PPTX sources ingest with text and slide numbers and no PDF preview, and `GET /sources/{id}/preview` answers 404 — which is the supported absent-converter state, not a failure (A158). The test config pins it to the empty string so a developer whose shell exports it cannot make the "no converter" case vacuous.

## Schema deviations from the spec (intentional, small)

| Change | Why |
|--------|-----|
| `users.password_hash` becomes **nullable**, plus `google_sub text unique` and `email_verified_at timestamptz` | A48. Google login creates users with no password, and the spec's `password_hash text not null` would make that impossible. `google_sub` is the stable Google identifier and is the **only** thing that may be trusted for account linking; `email` alone is not, because a Google account's email can change and an unverified match would be an account-takeover path. `email_verified_at` records *when* verification happened, which the A43 "verified email required before any AI action" rule needs as a timestamp rather than the existing boolean alone. |
| `users.is_admin boolean not null default false` | A7. Admin routes need an authority. |
| `events.task_id` gets `references tasks(id) on delete set null` | Spec left it an unconstrained uuid; a link without a FK drifts. **Ordering consequence:** `0012_tasks_*` must run before `0013_calendar_events`, or a fresh `sqlx migrate run` fails. |
| `jobs.dedupe_key text` + `unique` index (nullable) | A10. Singleton scheduled jobs (`monthly_grant`, `compact_change_log`, `poll_payment`) must not double-run across restarts or instances; a duplicate `monthly_grant` double-grants credits. |
| `pending_actions` gains `user_id`/`updated_at`/`deleted_at` + both sync triggers | The spec's DDL omits the `-- +sync` marker on `pending_actions`, but it is a synced entity: `Entity::PendingAction` (rank 16) requires it, and the spec says pending actions must be "visible and confirmable from any signed-in device". |
| New table `report_revisions` | The spec's conflict rules require that when a long text (`reports.body_md`) is edited on two devices, the losing version is kept "as a recoverable copy". There is no table for it in the spec's DDL. It is server-side recovery data: no triggers, not synced, like billing internals. |
| `chunks.embedding` dimension is a single migration constant (default `768`) | A2. Must equal the configured embedder dimension; one place to change. |
| `chunks` gains an `embedder text not null` column, and the dedupe index becomes a **non-unique** `index on chunks (embedder, content_hash)` replacing the spec's plain `content_hash` index | Two reasons. (1) The spec's dedupe rule ("skip re-embedding chunks whose content_hash already exists") would silently reuse vectors from a *different* embedding model after a provider switch, leaving mixed vector spaces in one table and corrupting retrieval. So the lookup must be keyed on embedder identity. (2) It must **not** be a unique constraint: `chunks` has no `user_id` (it is scoped through `source_id → sources.workspace_id → workspaces.user_id`), so uniqueness would be global across all accounts. The first user to upload a widely-shared textbook would make ingestion *fail* for every other user who uploads the same file, and the error would leak content existence across tenants. `source_id` is `not null`, so chunks can never be shared rows anyway. Dedupe is implemented as a lookup that copies the existing embedding into the new row, scoped to the same user by joining through `sources`/`workspaces`. |
| `change_log.origin_device_id` is filled from `current_setting('app.device_id')` set per transaction | Avoids adding a device column to every sync table just for the log. |
| New tables `reminders` and `reminder_deliveries` | A283. The spec's DDL has no reminder storage, and the server's copy is what makes a reminder fire when no client is running. Deliberately **not** `+sync`: a reminder is server-owned scheduling state, the client computes its own local notifications from synced rows, and an `Entity` variant would mean attaching a trigger from `0017_sync_triggers.sql`, which must stay the last trigger-attaching migration. Both therefore get a `documented` row in `crates/server/tests/schema.rs`, the `search_cache`/`syllabus_drafts` precedent. `reminders.dedupe_key` is `unique`, which is dedupe layer 1 of A285. |
| `log_change()` / `log_change_by_user()` take `pg_advisory_xact_lock(hashtext(user_id::text))` before inserting | Correctness, not tuning: `seq` is assigned by `nextval()` at insert time but rows become visible at commit time, so without the lock a pull cursor can permanently skip a lower seq that committed later. See roadmap § Sync protocol. |
| New table `cheatsheets` (+sync metadata) | The spec has no cheatsheet entity, but the print-PDF feature needs one to persist a generated document. Stores `title`, `scope`, `exam_date`, `depth`, `source_ids`, `status`, `error` and the object-storage keys for the rendered HTML and PDF. The rendered artifacts live in object storage (they are large and are not edited on-device), so only metadata syncs. |
| Citation format: numeric labels, not `[[chunk:<uuid>]]` | The spec's § Retrieval and chat states the same numeric-label rule; what this row pins is the implementation detail. Sending raw UUIDs costs ~40 tokens per citation and lets a model fabricate a plausible-looking UUID; numeric labels are cheaper and an unknown label is trivially rejected against the context the server sent. `crates/core/src/citations.rs` is therefore a label→chunk resolver. The structured `messages.citations` form from the spec is unchanged. |
| `usage_events` gains `prompt_version text` | The prompt version that produced each action, so a quality or cost regression can be attributed to a prompt change rather than guessed at (A38). Nullable, because not every action calls a model. |
| New table `email_verification_tokens` | The spec's DDL has no token store, and `/auth/verify-email` plus A48's "a Google-only account must verify its email before setting a password" rule both need one. Holds `token_hash` (SHA-256, never the token), `expires_at` and `used_at`, so a link is single-use and expiring. **Not `+sync`**: a verification token is a credential, and a client must never see or replay one through the change log. Appended as `0018` after `0017_sync_triggers.sql` without touching that migration's trigger array. |
| New table `login_tickets` | A48's callback runs in the system browser and must hand the app something. Putting an access or refresh token in the deep link would write a credential into browser history, referrer logs and the OS URL handler, so the callback redirects with an opaque single-use ticket and the app exchanges it over HTTPS for the real pair. Holds `ticket_hash` only, plus the declared device, a short `expires_at` and `used_at`. **Not `+sync`** for the same reason as above. |
| `crates/server/tests/schema.rs` `documented` list carries both new tables | That test's contract is "anything not in the spec's DDL must be a documented deviation", so a table added without a row here fails it. Both are listed in the test and in this table. |
| `jobs.kind` gains `generate_cheatsheet`, `render_cheatsheet_pdf` | Split so a PDF-rendering failure does not discard a successfully generated cheatsheet; the HTML is still usable and printable from a browser. |
| New table `search_cache`, plus `usage_events.cache_hit`/`search_tier`/`unresponsive_engines` | A40. The cache is **global, not per-user**: a query string carries no user data, so a per-user table would multiply storage by the user count for no benefit. `key` is `sha256(normalized_query \| provider \| max_results)` from `crates/core/src/search/normalize.rs`; `expires_at` carries the TTL and has its own index for the purge job. The three `usage_events` columns are what make the accounting honest: `cache_hit` keeps a free request visible in the margin report, `search_tier` names what actually answered, and `unresponsive_engines` records SearXNG's own list of engines that failed so silent degradation of the free path is a row rather than a user's complaint. **Not `+sync`**: server-side cost control, no client-visible entity. |

| New table `signup_attempts` (`ip`, `email_domain`, `created_at` + indexes on `(ip, created_at)` and `(email_domain, created_at)`) | A154/A43. The signup limiter has to survive a restart, and an in-process bucket does not — which is exactly what a signup farm waits for. Every attempt is recorded, including the ones that fail, because a farm's failures are the signal (R5's false-positive measurement reads them). It holds only `ip`, `email_domain` and `created_at` — no user id and no email address, because the attempts being counted include the ones that never became an account, and an address that failed to sign up is not ours to keep. Rows older than `SIGNUP_ATTEMPT_RETENTION_HOURS = 48` are pruned by the `reset_counters` job. **Not `+sync`**: it holds IPs and email domains, so it must never reach a device through the change log. Listed in `crates/server/tests/schema.rs`'s `documented` array. |
| `credit_ledger.period_key text` + `unique index on credit_ledger (user_id, period_key) where period_key is not null`; `workspaces.read_only` and `devices.read_only` (both `boolean not null default false`) | A152/A149. The monthly grant must be idempotent **by construction, not by scheduling**: the signup grant (A64) and the recurring `monthly_grant` job can both run inside one month, and `jobs.dedupe_key` only stops the *job* being enqueued twice. `period_key` is `'monthly:<local YYYY-MM>'` (free) or `'sub:<subscription_id>:<period start>'` (paid), and every grant is `insert … on conflict do nothing`, so a second grant is a no-op. The index is **partial** so the existing rows (`period_key = null`) are unaffected. The two `read_only` columns are the downgrade flag: `sources.read_only` has existed since `0007` and these are its siblings, set by `entitlements::recompute_read_only` and consulted by the write paths, never by a read. |
| `sources.preview_key text` | The spec's DDL already carries it; migration `0026` adds it to the tree. It is the object key of the PDF rendition LibreOffice produces for a PPTX or DOCX, so the client opens one media type for every source kind. Null when no converter is configured (A158) or when the source has no original file (a `url` source), and `GET /sources/{id}/preview` answers 404 in both cases rather than serving an empty document that would look like a scan. |
| `config/plans.toml` gains `[credits] monthly_rollover` | A153. The spec says "no rollover by default, configurable" and the config had no such key. Shipped as `false`; read by `jobs::handlers::grants::grant_period`, which writes the once-only `reason = 'expire'` row for the unspent monthly bucket before granting when it is off. |
| New table `change_log_watermark` (`user_id uuid primary key references users on delete cascade`, `min_retained_seq bigint not null default 0`, `compacted_at timestamptz`) | A165/A184. Compaction's per-user watermark: the seq below which this account's history is gone, which is what a cursor is compared against for 410. **Not a `+sync` table**: it is a server-side cursor fact with no client entity, so `0017_sync_triggers.sql` stays the last trigger-attaching migration and its array is untouched. `crates/server/tests/schema.rs` asserts it carries no triggers and lists it among the documented deviations. |
| `config` gains `CHANGE_LOG_RETENTION_DAYS` (90) and `CHANGE_LOG_TOMBSTONE_RETENTION_DAYS` (180), documented in `.env.example` | A184. The two retention windows are configuration, not constants, and both are pinned in `crates/server/src/testing.rs`'s override list so a developer's environment cannot change what a suite compacts. |
| `tasks.position int not null default 0` (migration `0028_tasks_events_settings.sql`) | A196. The spec's `tasks` DDL has no ordering column, and a breakdown inserts 3-8 subtasks in one transaction — so `order by created_at` is a random order, because every row of the batch shares the timestamp to the microsecond (the defect Phase 5 hit with `quiz_questions`, A100). `position` is an ordinary client-writable field: the client numbers them `0..n-1`, push carries it, and it is in `Entity::Task.payload_columns()` so it is not silently dropped by `write_columns` and does ship in a pull. |
| `user_settings` gains `quiet_start_hour` / `quiet_end_hour` (nullable ints, a pair) and `language text not null default 'en'` / `theme text not null default 'system'` (migration `0028`) | A202. The spec's DDL carries `language` and `theme` and `0012` dropped them; the settings screen requires quiet hours and the spec's DDL has no column for them. Quiet hours are a pair or neither (`check ((quiet_start_hour is null) = (quiet_end_hour is null))`) and the window may wrap midnight, so the reader tests membership and never `start < end`. All four are in `Entity::UserSettings.payload_columns()`: the row is synced, so a choice made on the phone has to be the choice the laptop uses. |
| Six `check` constraints on `user_settings` (migration `0028`): `user_settings_quiet_hours_paired`, `user_settings_quiet_hours_range`, `user_settings_language`, `user_settings_theme`, `user_settings_hours`, `user_settings_limits` | The bounds are enforced in `crates/server/src/settings.rs::validate_settings` first, so these are a **backstop** rather than the error path — a constraint violation would be a 500 from a statement that had already run, while a rule in the validator is the 400 the client can act on. They exist because the columns already had defaults and no bounds, and a `study_start_hour` outside 0-23 reaches Phase 11's planner as a negative window. The plan's Task 14 says "five"; the migration adds six, and the six are the accurate number. |
| `tasks.deleted_with_parent boolean not null default false` (migration `0029_tasks_cascade_restore.sql`) | A197/A214. Without it a restore cannot tell a child the cascade tombstoned from one the student deleted deliberately, so restoring a parent is either a false resurrection or a subtree that stays silently gone. It is **server-owned**: absent from `Entity::Task.payload_columns`, so a push cannot set it and a pull does not ship it. `0029` adds a column to an existing `+sync` table and attaches no trigger, so `0017_sync_triggers.sql` stays the last trigger-attaching migration and `crates/server/tests/schema.rs` needs no new row — the precedent `0021`–`0023` and `0028` each state in their own header. |

| `calendar_connections` (migration `0030_calendar.sql`) | A230-A249. | `syllabus_drafts` (migration `0031_syllabus_drafts.sql`) | A251. The spec's DDL has no table for the extraction, and the review step needs one that is **server-owned**: the model produced it, the student confirms it, and it has no client identity. Holds `source_id` (unique — the extraction is idempotent, so a retry `update`s the same row rather than appending a second draft), `status`, `extraction jsonb`, `error`, `prompt_version` and `credits_spent`. **Not `+sync`**: there is no `Entity` variant for it and adding one would mean attaching a trigger from `0017_sync_triggers.sql`, which must stay the last trigger-attaching migration. `crates/server/tests/schema.rs`'s `documented` list carries it, which is that test's contract — anything not in the spec's DDL must be a documented deviation. |

## Crate-list deviations

| Spec says | Plan uses | Why |
|-----------|-----------|-----|
| `ical` for parsing ICS | `icalendar` 0.17.14 for **both** parse and generate; `rrule` 0.14 for recurrence — **now pinned in `Cargo.toml` and `crates/core/Cargo.toml`** | `ical` 0.11 is dormant (last release Mar 2024); `icalendar` is actively maintained and already required for generation. This row was aspirational until Phase 10; the crates are pinned there now, for the same reason `headless_chrome` is: the feed is a document a client caches and the parser reads someone else's, so a minor upgrade must be a deliberate change with the acceptance test re-run. **`icalendar` needs its non-default `parser` feature for the import half** — without it `icalendar::parser::read_components` does not exist and both the feed round-trip test and the whole ICS import fail to compile. `rrule` is pinned explicitly rather than used through `icalendar`'s re-export, because the crate re-exports only a subset of `rrule`'s types, so relying on it would tie the expansion API to `icalendar`'s release cadence and could silently hand back a different version than A232's bound is written against. `rrule`'s `all(limit)` takes a `u16`, so `MAX_OCCURRENCES` is capped at 65535 by the crate rather than by the plan. |

## Out of scope (confirmed from spec)

Apple IAP, Google Play Billing, auto-renewing billing, audio overviews, lecture recording/transcription, realtime collaboration, Mac App Store / Microsoft Store, Linux, widgets/watch apps, OCR/camera scanning, on-device LLMs, offline chat/generation/uploads, multiple chat threads per workspace, non-Google OAuth, LMS integrations, browser extension, Stripe/international payments.

**Telegram and Discord reminder delivery (Phase 12, A288).** Both are granted by `config/plans.toml`
to Power and both are selectable in Settings, and neither has a transport. That is recorded rather
than silently skipped, and `GET /settings`'s `channels_available` is what makes it visible: a
delivery on either is recorded with `reason = 'channel_not_implemented'` and logged at `warn`, and
the settings screen offers only the channels that will fire. The revisit trigger is Phase 14's
deep-link work (the Telegram chat-id handshake, `t.me/<bot>?start=<ticket>` → a secret-token-verified
webhook) and, for Discord, a single POST to a user-supplied webhook URL validated by **host
allowlist** (`discord.com`/`discordapp.com`, https only) rather than by the private-network
blocklist.
